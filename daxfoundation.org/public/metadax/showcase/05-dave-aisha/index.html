Shift 4 — Blameless reviews + status updates
Aisha drafts first, you coach with questions
What you need
The checkout-errors incident from shift 3. Aisha knows it. Use it as the example throughout.
How it goes
01
Ask Aisha to write a blameless review on her own first: impact, timeline, what went well, contributing factors (as system gaps, not names), actions.
02
Read her draft. Check: does it name people? Do the contributing factors describe conditions and missing safeguards?
03
For any person-blame sentence, ask a question instead of rewriting: "What was missing in the system that let this reach production?"
04
Work through a status update together. She fills in the fields; you check it: what's affected, what we're doing, when's the next update.
05
Wrap up: ask what she'd do differently if this exact incident happened again next week.
Say this
"Walk me through your review. Which contributing factor do you think did the most damage before we caught it?"
"Not wrong — but can you write that as a gap in the system, not a gap in a person?"
Don't say this
"Sam shouldn't have merged that." Even as an example of what to avoid, it puts Sam in the room. Use the system frame instead: "the change reached production without a check on the payment path."

When it's tricky
IF: her review names a person
Ask: "What was missing in the system that let this change reach production?" Don't rewrite it for her.
IF: she gets defensive about naming the person
Acknowledge it: "You're right that someone made the change. Blameless means we fix what the system was missing — not that we pretend the change didn't happen." Then ask the system question.
IF: she's stuck and doesn't know how to start
Start with what went well: she rolled back in 6 minutes, the status update was clear. That unlocks the rest.
IF: you want to rewrite her review
Ask instead: "What would a canary check have caught here?" You're not the author. She is.
IF: the review is good but the status update is vague
Ask: "What did customers see? What are we doing right now? When will we update again?" Those three answers are the update.
IF: Aisha asks Dave how to run a log query
Flip it: "Show me how you ran it in shift 3." You don't know this tool better than she does.

Questions you might have
What if I genuinely know who wrote the bad code?
You can know. In the blameless review, the question is different: what made it possible for that code to reach production? That's the system gap.
A person making a mistake is not a safeguard. The test that didn't cover the payment path — that's a safeguard you can fix.
But what if there was no system gap — someone just skipped the checklist?
Then the system gap is: the checklist isn't enforced automatically. Why not? Could it be? That's the action item — not "person X needs to follow the checklist."
You can't build a reliable system by expecting individuals to never skip steps. You build the system so skipping a step is harder than doing it.
What if rolling back would break something else?
Check the rollback target before you run it. If you're unsure, post a quick update: "Assessing whether rollback is safe. Next update in 5 min." Then decide.
If rollback is genuinely risky, the path is a forward fix or a feature flag. But default to rollback — it's the fastest route to a known-good state.
How do I know if a rollback is safe?
Quick test: did this deploy touch the database schema or any shared state? If yes, rollback is riskier — check with a second engineer first. If no, rollback is usually safe to run.
How long should a blameless review take to write?
For an incident like shift 3, 30–45 minutes for a first draft is about right. Timeline and what-went-well are fast. Contributing factors take the most time — that's where the real work is.
If you're past an hour on a single incident review, you're probably going too deep. The review is a starting point for action items, not a forensic investigation.
What makes a good action item vs a weak one?
Good: specific, ownable, and tied to a system gap. "Add a payment-path smoke test to CI" — yes. "Be more careful next time" — no. If you can't assign it to a system or process, it's not an action item.
What if a contributing factor sounds like an excuse?
Good instinct. There's a real difference. "The test suite didn't cover the payment path" is a system gap. "We were moving fast" is a context note, not a gap you can fix.
Test: can you write a concrete action item for it? If yes, it's a contributing factor. If no, move it to context and keep going.
